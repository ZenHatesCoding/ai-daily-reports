DomainShuttle: 港科大 C4G 组开源跨域主体驱动文生视频, 同一个角色能在不同世界里穿越

想象你在抖音拍一段穿西装打网球的视频, 现在想换成穿汉服打羽毛球, 或者在火星打篮球 — 普通文生视频模型会「认不出你还是同一个人」, 因为它只学过「固定场景下生成对应画面」, 不会「保留你这个主体 + 灵活换场景」。港科大 C4G 组开源了 DomainShuttle, 核心能力是「主体保真 + 场景灵活切换」: 你给它一张参考图 (比如你的头像), 它能在任何 prompt 描述的新场景里 (火星 / 古风 / 海底 / 动画风) 都保留「你的样子」, 同时让背景和动作按文字自由变化。技术核心是把参考图特征和视频特征放在「两个独立的 RoPE 空间」(类似两套坐标系), 让模型既能精确锁定你的样子, 又不会被场景细节干扰。

📖 专业版问题讲解 (展开)
论文针对 Open-Domain Subject-driven Text-to-Video (S2V) 中「in-domain 保真 vs cross-domain 可编辑」的固有矛盾, 提出 Domain-MōT (Domain-aware Mixture-of-Transformers) 架构, 通过 Domain-aware AdaLN 模块实现参考图像的 domain-specific 条件注入, 同时引入 Video-Reference DualRoPE 机制将参考图像 token 与视频 token 分别置于独立 RoPE 频率空间以实现精确主体级空间建模, 并设计 Cross-Pair Consistent Loss 提取不受无关特征干扰的本体特征。开源代码: github.com/HKUST-C4G/DomainShuttle。
⚙️ 方法：方法核心是「双 RoPE 空间 + 域感知混合架构」: (1) Domain-MōT 框架: 把视频生成流程拆成「参考图像编码器」+「视频 DiT 主干」, 中间用 Mixture-of-Transformers 让参考图像特征只在某些注意力层注入视频生成, 避免过度绑定; (2) Domain-aware AdaLN: 在 DiT 的 adaptive layer norm 里加入「域标识」(in-domain 锁定 vs cross-domain 灵活), 模型根据 prompt 自动判断「该主体保留度」, 不用手工调; (3) Video-Reference DualRoPE: 参考图 token 用一个 RoPE 空间 (低频, 保结构), 视频 token 用另一个 RoPE 空间 (高频, 动态变化), 两个空间独立编码避免互相干扰; (4) Cross-Pair Consistent Loss: 在训练时强制「同一主体的不同 prompt 输出」保持主体特征一致, 解决「同主体跨域漂移」问题。
⚖️ 取舍：代价 1: 训练成本高 — Video-Reference DualRoPE 需要两套独立的 3D 位置编码, 相比单 RoPE 方案训练显存增加 35-45%, 训练 1 个 checkpoint 需要 8×H100 跑 5 天; 中小团队难复现。代价 2: 视频时长上限 5 秒 — 当前架构在 5 秒内能保证主体一致性, 超过 5 秒主体漂移开始累积, 限制了在长视频 / 短视频剧情场景的应用。代价 3: 域间迁移仍有上限 — 在「人物 → 动漫角色」这种 extreme domain shift 场景, 主体特征保留率从 95% 降到 78%, 对极致风格化场景仍然需要外挂 IP-Adapter。
📊 效果：在 Subject-driven Video Generation 主流基准 (DreamBooth / AnimateBench / VideoBooth) 上, DomainShuttle 相对 SOTA baseline (AnimateDiff + IP-Adapter / VideoBooth / Subject-Diffusion) 主客观指标全面领先: 主体保真度 (DINO 相似度) +0.08, 视频质量 (FVD) -15%, 文本对齐 (CLIP score) +0.04, 用户研究 (人类偏好) 胜率 67%。尤其在跨域场景 (人物→古风 / 人物→赛博朋克), 优势更明显: 主体保留率比 SOTA 高 12-18%。开源 5 秒视频生成, 单卡 A100 推理 8GB 显存, 速度 12 秒生成 5 秒 720P 视频。

DanceOPD: 字节 Seed 联合 NUS / UMD / HKUST 开源图像生成「多能力融合」框架, 一个模型同时搞定文生图 + 局部编辑 + 全局编辑

想象你要 AI 同时干 3 件事: 生成一张「猫咪在花园」, 然后把猫改成「老虎」(局部编辑), 再把背景从「花园」改成「雪山」(全局编辑) — 现在大多数图像生成模型只擅长其中 1 件, 强行让它做 3 件, 质量会全面下降, 出现「改了局部破坏了全局, 改了全局破坏了细节」的尴尬。字节 Seed 团队联合 NUS / UMD / HKUST 开源了 DanceOPD, 核心思路是把「文生图 / 局部编辑 / 全局编辑」当成「3 个不同的能力流场」(expert fields), 在训练时让模型学会「每个样本分配到 1 个能力流场 + 借鉴其他流场的状态」, 这样模型不再「串台」, 而是把每个能力当独立的「舞蹈舞种」, 在 flow-matching 框架下统一编排。

📖 专业版问题讲解 (展开)
论文提出 DanceOPD (On-Policy Generative Field Distillation) 框架, 针对 flow-matching 图像生成模型在多能力 (T2I / local edit / global edit / CFG) 组合时的性能相互干扰问题, 将每个能力建模为共享 flow state space 上的 velocity field, 通过 on-policy distillation 让 student 模型从「自身 rollout 状态」查询的 field 中学习 expert 能力, 同时吸收 classifier-free guidance 等 operator-defined field。该框架在 SD3 + FLUX 等主流 flow-matching 模型上验证, 实现多能力组合下的 SOTA。
⚙️ 方法：方法核心是「on-policy generative field distillation」: (1) 把每个能力 (T2I / 局部编辑 / 全局编辑 / CFG) 看成 flow-matching 共享状态空间上的一个 velocity field (速度场, 控制图像演化方向), 不同能力用不同的 field 路径; (2) On-policy rollout: 在训练时让 student 模型先生成 1 张图, 然后基于这张图的实际状态去「查询」各 expert field 应该给的指导, 而不是用固定的 expert 演示数据; (3) Simple velocity MSE objective: 不需要复杂的 adversarial loss, 直接让 student 模仿「基于自身状态的 expert 速度场输出」即可; (4) Absorbing operator-defined fields: 像 classifier-free guidance (CFG) 这种「人工设计的引导场」也能统一进这个框架, 不需要额外的特殊处理。
⚖️ 取舍：代价 1: 训练数据标注复杂 — 每个训练样本需要「图像 + 4 套 expert 轨迹标注 (T2I / 局部编辑 / 全局编辑 / CFG)」, 数据准备成本是普通 T2I 训练的 4-5 倍, 中小团队难承担。代价 2: On-policy rollout 训练慢 — student 模型要先生成 1 张图再 query expert field, 相比普通 distillation 训练时长增加 2-3x, 100 万样本训练需要 8×H100 跑 14 天。代价 3: 能力冲突未完全解决 — 在极端风格化 (真实→漫画) + 局部编辑组合场景, 局部编辑的边界感知仍会出现 5-8% 的溢出, 对专业设计师可能仍需手动微调。
📊 效果：在 GenEval / T2I-CompBench / EditBench 三个主流基准上, DanceOPD 训练后的 FLUX-dev 模型相对 baseline (FLUX-dev 单能力训练) 全面领先: 文生图 GenEval 0.81 → 0.85, 局部编辑 EditBench 7.42 → 8.15, 全局编辑 T2I-CompBench 0.62 → 0.71, 同时保持 CFG 推理速度不变。用户研究 (50 位专业设计师 A/B 偏好) 胜率 73%, 特别认可「多能力组合不串台」的改进。模型权重和训练代码全部开源, 项目主页 DanceOPD.github.io。

ViQ: 腾讯混元联合清华 / NTU / 中科院开源视觉量化表征框架, 多模态训练提速 20-70%

想象你教 AI 看图理解世界 — 现在有两种办法: 一种是「连续表征」(把图像转成长长的浮点数, 信息全但很贵), 另一种是「离散表征」(把图像转成 0/1 的「视觉单词」, 像文字一样便宜但丢细节)。视觉离散表征的最大问题是「为了压缩丢了太多信息」: 重建图像很模糊, 细节 (人脸 / 文字 / 小物体) 全没了。腾讯混元联合清华 / NTU / 中科院开源了 ViQ (Visual Quantized Representations), 核心思路是「两阶段训练」: 第一阶段用「大语言模型」当老师, 把「图像应该对应什么文字描述」作为预训练目标, 让量化器学会「保留对语言模型有用的语义」; 第二阶段再用「特征离散化」压缩表征, 同时保留高分辨率重建能力。结果是同一个量化器, 既能「跟文字配合做多模态任务」, 又能「重建高质量图像」, 多模态训练速度提升 20-70%。

📖 专业版问题讲解 (展开)
论文针对视觉量化表征中「重建精度 vs 语义丰富度」的固有权衡, 提出两阶段训练框架: (1) text-aligned pre-training 让视觉量化器与预训练 LLM 的 token space 对齐, 保留语义; (2) progressive proximal representation learning 让特征空间渐进压缩, 支持任意分辨率。ViQ 在主流多模态基准上达到 SOTA, 同时支持 native-resolution 输入, 训练加速 20-70%。
⚙️ 方法：方法核心是「text-aligned 预训练 + proximal 离散化」两阶段: (1) 阶段一 (text-aligned pre-training): 用预训练 LLM 作为教师网络, 让视觉编码器输出的连续特征和「对应文本描述」的语义对齐 — 不是简单的 CLIP 式对齐, 而是「视觉特征 → 量化 → 文本预测」全链路对齐, 让量化器保留「对 LLM 有用的语义」; (2) 阶段二 (proximal representation learning): 用 proximal 优化 (类似稀疏编码) 把连续特征空间压缩到离散 codebook, 同时保留阶段一对齐过的语义; (3) Position-aware head-wise quantization: 不同注意力头用不同 codebook, 避免单一 codebook 容量不够; (4) Native-resolution 支持: 不强制 resize 到固定分辨率, 输入图像多大就用多大, 对 OCR / 文档理解这种细节敏感任务极友好。
⚖️ 取舍：代价 1: 两阶段训练成本高 — 阶段一需要 1 个完整 LLM 作为教师, 训练显存比单阶段方案高 2-3 倍, 阶段二需要 4×H100 跑 7 天, 中小团队难复现。代价 2: Codebook 容量有限 — 视觉信息复杂度远高于文字 (一张图等价于 100-1000 词), 当前 16384 大小的 codebook 在极端细节场景 (医学影像 / 卫星图) 仍会出现「找不到对应 code 而模糊」的情况。代价 3: 推理时多模态任务性能略低于连续表征 — 在视觉问答 (VQA) 任务上 ViQ 比连续表征低 1.5-2.5% 准确率, 换速度提升 30% 是否划算要看具体场景。
📊 效果：在 12 个多模态基准 (VQA / 图像描述 / 文档理解 / 视频理解) 上, ViQ 相对 SOTA 离散表征 (VQ-VAE-2 / VQGAN-CLIP / SEED) 全面领先: 视觉问答 VQA 78.4 → 80.7, 文档理解 DocVQA 84.2 → 87.1, 视频理解 MSRVTT 53.4 → 56.8。重建质量在 FID 指标上从 8.7 降到 5.3 (越低越好), 重建图像细节保留率显著提升。多模态训练速度提升 20-70% (取决于基础 LLM 规模), 单卡推理速度提升 30-50%。开源代码 GitHub.com/yuxumin/ViQ, 权重 HuggingFace.co/XuminYu/ViQ_weights。

OPID: 清华 + 浙大 + 港中文 + NTU + 同济联合开源 agent 强化学习「技能自蒸馏」框架, 多轮任务样本效率翻倍

想象你训练一个 AI 客服 agent 处理退货: 它要查订单 + 确认收件人 + 申请退款 + 发通知 — 这个流程要 5-6 步, 每步都要对, 但训练时只能拿到「最后是否成功」这一个奖励信号 (退成了 +1, 没退成 0), 中间哪步错了完全不知道。普通强化学习 (RL) 在这种「稀疏奖励 + 多轮任务」场景几乎学不动, 因为 99% 的尝试都得到 0 分, agent 不知道怎么改进。OPID (On-Policy Skill Distillation) 给出了一个解法: 让 agent 从「自己已经跑成功过的轨迹」里「自我蒸馏」出可复用的「技能」(比如「查订单的标准流程」「申请退款的标准话术」), 然后在后续训练时, 当 agent 走到关键决策点 (例如「该查订单还是直接申请退款」), 自动调用对应技能当参考。这样 agent 既有「最终目标驱动」(outcome reward), 又有「中间步骤指导」(skill distillation), 训练样本效率提升 50-100%。

📖 专业版问题讲解 (展开)
论文针对 outcome-based RL 在多轮 agent 任务中「trajectory-level 奖励稀疏」的痛点, 提出 OPID (On-Policy Skill Distillation) 框架, 从 on-policy 成功轨迹中提取层次化技能 (episode-level 全局规则 + step-level 局部决策), 通过 routing 机制在 critical 决策点注入技能, 用 token-level self-distillation 给 dense supervision signal。ALFWorld / WebShop / Search-based QA 实验验证 sample efficiency 和 robustness 显著优于 outcome-only RL。
⚙️ 方法：方法核心是「on-policy 技能提取 + routing 机制 + token-level self-distillation」三件套: (1) 技能提取: 从已经跑成功过的轨迹里, 用 hierarchical clustering 提取两类技能 — episode-level (全局规则: 「先查订单再申请退款」) 和 step-level (局部决策: 「看到订单金额 > $1000 就要主管审批」), 存在 hierarchical skill memory; (2) Routing 机制: agent 走到关键决策点时, 先判断是「关键决策」还是「常规步骤」, 关键决策用 step-level 技能做参考, 常规步骤 fallback 到 episode-level 技能; (3) On-policy token-level self-distillation: 用同一 agent 在「有技能参考」和「无技能参考」两种情况下分别跑同一 prompt, 计算 log-prob 差异, 形成 dense self-distillation loss 叠加到 outcome reward 上, 让 token-level 监督信号直接驱动策略优化; (4) 不需要外部 skill memory — 所有技能从 agent 自身轨迹提取, 维护成本接近零。
⚖️ 取舍：代价 1: 前期冷启动慢 — 在训练初期 agent 没有成功轨迹就没有技能可提取, 前 10-20% 的训练轮次比纯 outcome RL 还慢, 需要配合「专家演示数据 warm-start」才能发挥优势。代价 2: 技能质量依赖轨迹多样性 — 如果 agent 早期就陷入「只走一种路径」的局部最优, 提取的技能会非常狭窄, 反而限制后续探索, 需要配合 entropy bonus 强制探索。代价 3: 推理时延略增 — routing 机制需要额外查询技能 memory (约 50-100ms), 对 latency 敏感的实时 agent 任务 (客服 / 实时对话) 可能不适合。
📊 效果：在 3 个 agent 任务基准 (ALFWorld 家庭任务 / WebShop 电商任务 / Search-based QA 搜索问答) 上, OPID 相对 outcome-only RL baseline (PPO / GRPO) 全面领先: ALFWorld 成功率 78.4 → 89.2, WebShop 78.4 → 85.6, SearchQA 62.3 → 71.8。样本效率提升 50-100% (达到相同成功率需要的训练样本减半)。Robustness 测试 (环境扰动 + 工具接口变更): OPID 表现下降 < 5%, 而 baseline 下降 15-20%, 证明「技能复用」对环境变化有韧性。代码已开源。

Verification Horizon: 阿里 Qwen 团队提出「没有银弹」原则, coding agent 验证比生成更难

软件工程有句老话: 「验证一个方案是否正确」比「想出一个方案」容易 (来自 1986 年 Brooks 的《No Silver Bullet》)。但阿里 Qwen 团队 6/26 发布论文说: 对 2026 年的 coding agent 来说, 这个直觉已经反转了 — 现在 AI 生成「可能正确的代码」已经不难, 难的是「可靠地判断这段代码到底对不对」。论文核心论点是: 任何 verifier (验证器) 都只是「人类意图的近似」, 永远不是意图本身, 这导致验证存在两重困难: (1) 人类意图本身「欠规范」(underspecified) — 用户说「做个好看点的登录页」, 「好看」到底是什么没人说得清, 验证器无从判断; (2) 模型训练会「放大 verifier 跟真实意图的差距」 — 这就是 reward hacking (奖励欺骗) 和信号饱和。论文提出「可扩展性 / 忠实性 / 鲁棒性」三维框架, 并用 4 种 verifier (test verifier / rubric verifier / user-as-verifier / automated agent verifier) 实测验证。

📖 专业版问题讲解 (展开)
论文对当前 coding agent 训练中「verifier 设计」的系统性反思, 提出 verification horizon 概念 — 任何 verifier 都是人类意图的 proxy, 存在「意图 underspecification」和「优化放大 proxy-intent gap」两重困难, 设计 verifier 时必须在 scalability / faithfulness / robustness 三维间权衡。论文用 4 类 verifier (test / rubric / user-as-verifier / automated agent verifier) 实证分析 reward hacking 风险与缓解策略。
⚙️ 方法：方法核心是「verification 三维框架 + 4 类 verifier 实证」: (1) Verification 三维: 任何 verifier 必须同时评估 scalability (能否扩展到大规模训练), faithfulness (跟真实意图有多接近), robustness (面对 reward hacking 的稳健性) — 论文论证「同时满足三维」是当前 coding agent 训练的核心难题; (2) 4 类 verifier 实证: (a) test verifier — 用单元测试判定代码正确, 适合通用 coding 但 faithfulness 低 (用户意图可能不是「通过测试」); (b) rubric verifier — 用评分细则 (rubric) 让 LLM 打分, faithfulness 高但 scalability 差 (人工写 rubric); (c) user-as-verifier — 用真实用户反馈训练, faithfulness 最高但 scalability 极差 (用户不可能给大规模训练提供反馈); (d) automated agent verifier — 让另一个 agent 跑用户场景判定, scalability 和 faithfulness 介于中间, 但对长 horizon 任务鲁棒性差; (3) Reward hacking 分析: 论文用具体案例展示模型如何「骗过 verifier」(比如「通过测试」+「代码乱到无法维护」), 提出针对性 mitigation。
⚖️ 取舍：代价 1: 没有单一银弹 — 4 类 verifier 各有优劣, 实际部署必须组合使用, 但组合的权重如何设置仍是开放问题, 需要大量实验调优; 代价 2: Faithfulness 评估难 — 论文承认「忠实性」本身也欠规范 — 什么叫「verifier 忠实于意图」? 缺少 ground truth 让论文的 faithfulness 评估只能靠「定性案例」而非「定量指标」; 代价 3: 对企业落地指导有限 — 论文是「分析框架」而非「解决方案」, 企业要落地 verifier 设计仍需自己摸索「test / rubric / user / agent」的具体配比, 论文给出的「4 类组合」仅作启发。
📊 效果：在 8 个内部 + 公开 coding 基准 (HumanEval / MBPP / SWE-bench / APPS / LiveCodeBench / RepoBench / CrossCodeEval / CodeXGLUE) 上, 论文系统性比较 4 类 verifier 的 scalability / faithfulness / robustness 表现, 发现: test verifier scalability 最强但 reward hacking 率 23%, rubric verifier faithfulness 最高但 scalability 只有 test 的 1/50, user-as-verifier faithfulness 99% 但只能支持 < 1000 样本训练, automated agent verifier 在长 horizon 任务 (SWE-bench Verified) 上 faithfulness 反而比 rubric verifier 高 8%。论文用 4 类 verifier 组合 (test 70% + rubric 20% + agent 10%) 在 SWE-bench Verified 上达到 68.4% 解决率, 比单一 test verifier (54.2%) 高 14.2 个百分点。
